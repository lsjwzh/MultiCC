# 会话调度读模型：待实现约束

状态：设计记录，尚未接入生产，也不代表调度迁移完成。

当前实验基础：Rust 存储增加绑定单会话读事务的临时快照令牌，顺序分页扫描
`pending`/`leased` 索引中的 ID、序号及排序值，每页最多 128 条。排序值仅从
不超过 64 KiB 的活动记录提取，较大或拆分的记录直接报错；消息正文不送到 Node。
扫描进度由 Rust 持有，拒绝调用方指定游标或状态，最后一页仅表示该 SQLite
快照的候选索引遍历完成，并不证明调用方已保存每页。实验准备写入入口要求完成扫描、
匹配令牌和起始 revision，再由现有事务检查 revision 与 `data_version`；普通
prepare 在扫描期间拒绝使用，令牌在事务结束或重新开始时失效。此版本检查只可在
已验证的隔离所有者前提下考虑，不能解决同进程混用 SQLite 驱动导致的锁问题。
扫描开始时额外从不超过 64 KiB 的单条会话记录投影活动投递 ID 和优先项 ID，
未支持的类型、超长记录或非规范字符串直接报错，完整记录不送到 Node。该接口
尚未经 CI 验证，不含分类和宿主回调事实，完成扫描也不表示读模型已经就绪；
64 KiB 限制目前排除大消息，必须有兼容方案后才能替换生产调度。
超长 ID、无效序号及特殊字符串需要可靠的兼容方案；现阶段不能用它替换任何
生产调度逻辑。

现有 `admit`、`complete`、`reorderQueued` 和 `recover` 在事务回调中同步读取
宿主事实并更新状态。等待异步预读后再调用这些回调，会让调用方排队的微任务先
运行，改变问题归属、时钟和分类结果；把当前逐行代理访问原样搬进同步 Rust 则
继续阻塞 Node。现有回归分别记录这两类失败。

下一步须先由 Rust 所有者维护共享读模型：

1. 对会话和活动 outbox 建立按会话分组的有界元数据与顺序索引；首次构建和失效
   重建在后台完成，不向 Node 复制消息正文。启动时未就绪应明确等待或失败，不能
   使用未经校验的旧值。
2. 所有写命令、兼容写入及恢复路径在同一事务协议下更新或失效模型。处理外部
   SQLite 写入时，由独立所有者在事务边界检查数据库版本，并在提交时验证读模型
   的版本；冲突不能套用旧模型，更不能自动重放结果不明的提交。
3. 在原有事务回调的观察时刻读取时钟、待回答问题和分类状态；预先准备的仅能是
   与版本绑定的数据库事实。不得先读取宿主事实再等待后台扫描，或在回调前等待
   扫描导致宿主事实被后续微任务改变。
4. 重排和 W 完成目前可能逐条重写整个队列。需要设计可兼容历史 `queueOrder`、
   `blockedByUserInput` 和现有读写者的索引/投影，避免仅将不受限扫描移到同步
   N-API；旧数据和直接读取必须得到一致结果。
5. 恢复过程目前逐会话调用宿主状态回调。若要异步分批而不改变快照时序，应先将
   对应事实及全部写入者迁入 Rust 管理的版本化状态；简单分批会改变观察到的值。

验收必须同时覆盖真实 SQLite 的事务原子性、外部并发写、回调顺序、特殊 JS 值、
1,000 条及更大队列的事件循环延迟，并与同等条件下的现有实现对比。不能只以静态
源码断言通过，或只以 Rust 实现替换 JavaScript 循环作为完成标准。
