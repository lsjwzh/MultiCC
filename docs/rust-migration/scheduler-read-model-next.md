## 工作区中的后台构建基础（尚未接线）

`scheduler_read_model.rs` 增加按 session 与版本绑定的有界元数据缓存：
重建时清除旧值，代次和失效 epoch 阻止迟到结果覆盖新构建；版本不匹配
会丢弃对应槽位；槽位、行数和缓存持有的分配容量分别限额。读者持有的
`Arc` 和构建过程内存不由缓存预算约束，提交时仍须在同一个数据库版本
协议下重新验证，不能凭一份曾经命中的 `Arc` 提交。

`orchestration_store/schedule_background.rs` 增加独立只读连接上的后台
快照构建，单次上限 4,096 行、同进程最多四个工作线程，按 16 行分页检查
取消；它只返回排序元数据，不包含消息正文。SQLite 快照只携带读取时的
revision，**不能单独证明与所有者连接的 data_version 一致**。16 MiB 以上
记录和现有扫描不支持的标识符仍然明确报错。独立所有者的多个会话现已
共享一个缓存，现有写命令及未知命令执行前保守失效，失败和回滚也失效；
新会话打开可能触发升级，打开前也会失效。所有者协议由 6 升至 7，addon
与网关必须同批构建。后台快照本身仍没有生产调用者，也没有共享监控连接
或提交路径接线，不得将其用于生产调度或关闭四个所有权门禁。

`schedule_guard.rs` 提供实验性写事务内 revision/data_version 复核，要求
SQLite 已持有写锁；多会话模式用独立、无事务的监控连接观测所有写入。
调用方必须自行保证连接指向相同文件，并把该监控连接与构建、写入失效
和提交接成单一协议。后台快照在 Unix 上持有文件句柄并在打开前后和读取
后检测普通路径替换；SQLite 自身的 `SQLITE_FCNTL_HAS_MOVED` 检查可拒绝
“SQLite 打开替换文件后原路径恢复”的 ABA 例子，并在写事务复核 writer
和 monitor。该接口在不支持的 VFS 上拒绝；Unix VFS 的路径/句柄核验仍
是多次独立观察，不能排除恶意并发重命名或跨设备同 inode 的竞态。非 Unix
平台暂时明确拒绝此实验。该文件身份检查尚不足以支持生产切换。
此外比较 SQLite 自报的数据库文件名与锚定句柄，避免把未发生移动但指向
另一数据库的 monitor 当作同一文件；上述比较同样不是原子的。
此外，当前 `start` 在调用线程打开锚定文件并读取路径元数据，可能因慢文件系统
阻塞；生产接线前必须将这部分安全地移出同步调用，同时保留与所有者文件的绑定。

活态事实尚未迁入独立所有者：`sessionWorkHost.recoveryState` 同时读取
`RustSessionRecords` 在 Node 进程内持有的活 JS 记录、`userInputSignalHost`
的待回答问题和 `chatSessions` 的 `_currentTaskId` / 轮次；分类状态和
信号的写入经 `setTaskState`，而 `src/classify/state-machine.js` 与
`src/task-context-host.js` 仍直接写入部分活态字段。独立 SQLite 所有者
无法直接读取这些引用。迁移时须将全部写入者和启动恢复纳入同一版本化
状态协议，并在原本的同步观察时刻确定事实，不能简单提前快照或增加一次
异步等待来宣称不再回调 Node。

当前实验基础：Rust 存储增加绑定单会话读事务的临时快照令牌，顺序分页扫描
`pending`/`leased` 索引中的 ID、序号及排序值，每页最多 128 条。排序值仅从
不超过 64 KiB 的活动记录提取，较大或拆分的记录直接报错；消息正文不送到 Node。
扫描进度由 Rust 持有，拒绝调用方指定游标或状态，最后一页仅表示该 SQLite
快照的候选索引遍历完成，并不证明调用方已保存每页。实验准备写入入口要求完成扫描、
匹配令牌和起始 revision，再由现有事务检查 revision 与 `data_version`；普通
prepare 在扫描期间拒绝使用，令牌在事务结束或重新开始时失效。此版本检查只可在
已验证的隔离所有者前提下考虑，不能解决同进程混用 SQLite 驱动导致的锁问题。
扫描开始时额外从不超过 64 KiB 的单条会话记录投影活动投递 ID 和优先项 ID，
未支持的类型、超长记录或非规范字符串直接报错，完整记录不送到 Node。该接口
尚未经 CI 验证，不含分类和宿主回调事实，完成扫描也不表示读模型已经就绪；
64 KiB 限制目前排除大消息，必须有兼容方案后才能替换生产调度。
超长 ID、无效序号及特殊字符串需要可靠的兼容方案；现阶段不能用它替换任何
生产调度逻辑。

实验接口可显式传 `prepareLargeRecords: true`：快照内单条记录上限提高到
16 MiB，并读取拆分记录的原始正文后只返回调度字段。未传选项时原有 64 KiB
上限及拒绝拆分记录的行为不变；缺失正文、字段与索引不一致及超过上限仍报错。
此选项在独立所有者进程使用保留 JS 重复键和 UTF-16 语义的解析器，测试覆盖
大记录、转义重复键、拆分正文、正文不外传与外部写冲突。**它仍是同步所有者
请求，会阻塞共享所有者的其他请求；它不是后台读模型，也未接入生产调度。**
16 MiB 以上仍需兼容方案，且必须完成下述全部条件才能使用。
实验准备路径使用 Rust 的 JSON 根字段投影：未选中的消息正文仍完整验证，但不
构造对应字符串和对象树；选中字段的重复键、转义及孤立代理项沿用原解析器。
SQLite 读取仍需在所有者进程中取得完整记录，此优化不提供异步或常量内存保证。

现有 `admit`、`complete`、`reorderQueued` 和 `recover` 在事务回调中同步读取
宿主事实并更新状态。等待异步预读后再调用这些回调，会让调用方排队的微任务先
运行，改变问题归属、时钟和分类结果；把当前逐行代理访问原样搬进同步 Rust 则
继续阻塞 Node。现有回归分别记录这两类失败。

下一步须先由 Rust 所有者维护共享读模型：

1. 对会话和活动 outbox 建立按会话分组的有界元数据与顺序索引；首次构建和失效
   重建在后台完成，不向 Node 复制消息正文。启动时未就绪应明确等待或失败，不能
   使用未经校验的旧值。
2. 所有写命令、兼容写入及恢复路径在同一事务协议下更新或失效模型。处理外部
   SQLite 写入时，由独立所有者在事务边界检查数据库版本，并在提交时验证读模型
   的版本；冲突不能套用旧模型，更不能自动重放结果不明的提交。
3. 在原有事务回调的观察时刻读取时钟、待回答问题和分类状态；预先准备的仅能是
   与版本绑定的数据库事实。不得先读取宿主事实再等待后台扫描，或在回调前等待
   扫描导致宿主事实被后续微任务改变。
4. 重排和 W 完成目前可能逐条重写整个队列。需要设计可兼容历史 `queueOrder`、
   `blockedByUserInput` 和现有读写者的索引/投影，避免仅将不受限扫描移到同步
   N-API；旧数据和直接读取必须得到一致结果。
5. 恢复过程目前逐会话调用宿主状态回调。若要异步分批而不改变快照时序，应先将
   对应事实及全部写入者迁入 Rust 管理的版本化状态；简单分批会改变观察到的值。

验收必须同时覆盖真实 SQLite 的事务原子性、外部并发写、回调顺序、特殊 JS 值、
1,000 条及更大队列的事件循环延迟，并与同等条件下的现有实现对比。不能只以静态
源码断言通过，或只以 Rust 实现替换 JavaScript 循环作为完成标准。
