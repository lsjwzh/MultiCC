# Rust CPR 实验版与测试方法

更新：2026-10-23（初稿：2026-10-22）

> 2026-11-06 注：Node 后端已删除，Rust 是唯一实现。下文的 Node 选项、`MULTICC_CPR_BACKEND`
> 和 `/api/settings/cpr-backend` 设置入口仅作为当时实验过程保留，代码中已不存在。

## 当前状态

MultiCC 新增一份独立的 Rust CPR 代理内核，通过现有 napi-rs 原生模块嵌入。原来的 `cli-provider-router`（CPR）Node 实现保留，默认仍使用 Node。显式选择 Rust 后，实验版才参与代理请求。

代理内核提交 `ef6c4619` 已经由 `7469bb0a` 合入 MultiCC 的 main；CPR 独立仓库不含这份 Rust 实现。本批提交包含新增的全局设置入口、配套原生接口及对比工具和报告。提交前已 rebase 到主线 `ce0df002`，组合回归 88/88、浏览器 3/3 及相关治理检查再次通过；本批改动尚未合入 main 或部署。没有修改运行服务的配置，也没有重启 MultiCC。真实账号验收留给用户启用后进行。

## 全局设置入口、开关与回退

入口位于 Web 的「设置 → 全局配置 → CPR 代理」，提供一个小按钮：默认显示「试用 Rust」，选择 Rust 后显示「使用 Node」，可随时保存回退选择。入口随本轮设置代码及匹配原生模块交付后可用；现有运行进程需要用户手动重启以加载新接口。

按钮只保存下一次启动的选择。界面分开展示「当前：Node」和「当前：Node · 重启后：Rust」等状态，不会把保存成功显示成运行时已经切换；保存、撤回选择或保存失败均不会自动重启。原生能力未就绪时，界面禁用启用 Rust 的操作并显示原因。若原生模块连设置接口也缺失，则返回接口未就绪错误，需先更新模块。

`GET /api/settings/cpr-backend` 返回当前版本、已保存版本、是否需要重启及 Rust 能力状态；`POST` 仅接受 `backend: "node" | "rust"`，通过 Rust 校验后复用宿主已有的原子配置写入接口。不会写入其他请求字段，也不会将其他环境配置返回给浏览器。

按钮保存的仍是下面这个环境变量，也可在实际运行服务读取的环境配置中手动设置：

```dotenv
MULTICC_CPR_BACKEND=rust
```

回退时改成：

```dotenv
MULTICC_CPR_BACKEND=node
```

删除这一项也会恢复默认 Node。只接受 `node` 或 `rust`（忽略大小写及两侧空格），非法值会报错。开关在进程创建代理运行时时读取，更改后需要用户手动重启服务；不支持正在进行的请求中途切换实现。

配置位置依运行方式确定：源码服务通常读取服务目录的 `.env`；指定 `MULTICC_ENV_FILE` 时以实际配置文件为准；standalone 和桌面版使用其用户数据目录的 `multicc.env`。已有进程环境中的值优先于文件配置；如果 launchd/systemd 或启动 shell 显式设置了同名变量，还需调整该启动环境，否则重启后文件选择可能仍被覆盖。不要把 `.env` 写进任务工作树，也不要依赖临时 shell 中的变量必然传到已注册的 launchd/systemd 服务。

该开关与现有 `MULTICC_PROVIDER_ROUTER_MODE=legacy|shadow|cpr` 分开：原有路由模式和管理功能保持原来的选择，只为 Claude/Codex 协议代理选择 Node 或 Rust 实现。全局设置不会自动改变默认实现。

显式选择 Rust 后，原生模块缺失、不可加载或 CPR 接口版本不匹配都会明确报错，不会在后台改用 Node。需要回退时显式改回 `node` 并由用户重启。此开关不改变 SQLite 等其他 Rust 功能的后端选择。

## 已实现的范围

这是一份针对 MultiCC 实际使用路径的 CPR 代理内核，并非把 CPR 的全部管理接口重写成了 Rust。

- Claude Messages：路由解析、子代理模型解码、供应商模型别名与上下文后缀改写、凭据请求规划、请求头整理、HTTP/TLS 转发。
- Codex 原生 Responses 和 Responses 兼容模式：供应商配置解析、命名子代理路由、请求整理、输出前的繁忙退避重试及兼容结束事件。
- 响应旁听：SSE 跨块 UTF-8、文本／推理／工具增量、缓存及普通 Token 用量、流内失败和限流头观测。正常代理路径按原始响应字节交付。
- 传输生命周期：连接与首包时限、客户端取消、输出背压、代理关闭、错误正文完整转发；超大错误不进入修复重试。
- 网络出口：复用宿主统一网络策略及官方账号专用出口插件的解析结果；Rust 自己建立连接，不创建 Node Agent。出口解析失败会终止请求，不会静默直连。

已退役的 Chat → Responses 桥不在 Rust 实验版支持范围，遇到该模式明确返回错误。需要该历史能力的配置应继续使用 Node。

CPR 的管理、接管、配置物化，以及 Codex 官方 OAuth 的宿主专属 relay 仍使用原有实现，不受此开关替换。不能把这些路径的成功归为 Rust 代理验证。

## Node 兼容层的保留原因

`src/providers/rust-cpr.js` 连接 Express 请求／响应、现有宿主授权、凭据读取与恢复回调、历史修复钩子、出口策略和用量事件。它调用已有宿主接口；新增路由规划、协议处理及网络传输核心位于 `native/cpr`。

保留这些 Node 接口是迁移桥接的需要：JavaScript 回调、Express 对象和当前 OAuth 管理器不能直接作为 Rust 业务对象传递。该层没有新建一套独立的账号或调度状态。Rust 通过异步 N-API 接口运行，网络 I/O 由 Tokio 执行，大请求的解析与序列化移至后台任务。

后续只有在宿主授权、账号凭据及事件总线提供明确的 Rust 接口，并完成同等契约验证后，才继续收缩这部分 Node 桥接；本次不改变它们的所有权和生产默认值。

（2026-11-06 起已删除：CPR 后端设置入口、`native/cpr/src/settings.rs` 与 `cprBackendSettings` 原生接口随 Node 后端一起移除，`MULTICC_CPR_BACKEND` 不再被读取。）原文：设置入口的新增校验、允许保存的键和状态生成均在 `native/cpr/src/settings.rs`，经 `cprBackendSettings` 原生接口调用。`src/routes/cpr-backend-settings.js` 仅保留 Express 请求／响应适配、原生能力查询和已有 `readEnvFile`／`writeEnvFile` 的调用：宿主目前仍由 Node 统一解析配置文件位置并原子保存，直接另建一份配置写入实现会分叉现有的桌面版、standalone 与源码路径。待宿主配置读写提供统一 Rust 接口并完成兼容验证后，可移除这部分读写桥接。该纯函数输入很小，使用同步 N-API；代理网络传输仍为异步。

## 构建与打包

源码版 `./multicc start` 沿用源码指纹缓存及自动构建流程，缓存位于主仓库 `data/rust-source/`。即使显式使用 Node SQLite，只要选择 Rust CPR，也必须提供或构建原生模块。源码构建需要 Rust/Cargo 和本平台链接工具。

standalone／桌面安装包必须携带包含 CPR 接口的目标平台原生模块，用户无需安装 Rust。源码缓存探测和打包校验检查 `cprProtocolVersion` 与 `cprCreateExchange`（2026-11-06 前还检查已删除的 `cprBackendSettings`），旧模块不能冒充本轮产物。本轮仅构建和测试了 macOS ARM64 模块，尚未制作包含本轮 CPR 设置入口的新完整发布安装包；此前 SQLite／核心 Rust 的 Intel 包验证不能代替 CPR 验证。

本机测试产物：

测试时 `MULTICC_RUST_ADDON` 指定运行时加载的单个模块，`MULTICC_RUST_PREBUILT_DIR` 指定打包复制模块的父目录；同时验证运行和打包时两者应指向同一份构建。只设置前者不能保证打包步骤复制新模块。

## 用户启用后的验收重点

合入并部署设置入口及匹配原生模块后，由用户选择测试实例，在「设置 → 全局配置 → CPR 代理」点击「试用 Rust」并手动重启，也可使用同一环境变量。建议覆盖 Claude 第三方与官方账号、Codex 原生 Responses、子代理、工具调用、长流式回复、中途取消、额度与用量，以及专用代理出口。可点击「使用 Node」并手动重启进行比较。

真实供应商账号、实际长会话、Windows／Linux／Intel 平台和新完整安装包尚未验收。2026-10-23 已完成当前 Node／Rust 实现的本地隔离对照，详见 [对比报告](rust-cpr-comparison-2026-10-23.md)：Rust 长上下文路径较慢，部分并发场景吞吐提高；还发现 Codex 错误格式和增量 UTF-8 解码存在差异。不能据此声称语言本身或真实聊天速度普遍提升。生产默认值继续保持 Node，后续是否改默认须先解决契约差异并完成客户端验收。
