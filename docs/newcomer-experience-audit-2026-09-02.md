# MultiCC 新手体验审计与改进方案

> 审计日期：2026-09-02  
> 目标用户：不熟悉终端、Git、CLI 和本地服务的办公型知识工作者  
> 覆盖范围：了解产品 → 安装主机端 → 首次启动 → 接入 AI → 创建工作区 → 创建对话 → 完成第一个任务 → 理解进度与结果 → 错误恢复 → 手机 App 连接与日常使用

## 1. 结论先行

MultiCC 当前是一套能力很强的本地 AI 工程控制台，但还不是一套让非技术用户能够独立完成安装和首次使用的消费级产品。

真正的问题不是“帮助文字不够”，而是产品把自己的内部实现模型——`Fleet`、Git 仓库、worktree、branch、CLI、Provider、session、Terminal、merge——过早地交给了用户。懂开发的人能把这些概念拼成正确操作，不懂程序的人则会在获得第一次价值之前连续做出多个自己无法判断对错的技术选择。

建议把下一阶段的北极星定义为：

> 一位由同事告知 MultiCC、但不懂终端和 Git 的办公用户，能够在 5 分钟内进入一个可用的 AI 对话，成功完成一个安全、可观察、可撤销的首次任务；过程中不需要理解 CLI、Provider、worktree 或 Access Token。

最优先的不是继续增加入口，而是做四件事：

1. 区分“安装主机的人”和“只连接使用的人”，为两类人提供不同入口。
2. 增加真正闭环的首次设置向导，先验证环境，再允许进入首页。
3. 默认提供“基础模式”，只展示用户任务；把工程能力渐进披露到“高级模式”。
4. 让首次任务以可验证的成功结束，而不是以“创建了一个 session”结束。

## 2. 用户画像与使用预期

### 2.1 典型用户

本审计中的“办公用户”具备以下特征：

- 会安装常见桌面软件和手机 App，会扫码、登录和选择文件夹。
- 能用自然语言描述“整理资料、生成周报、分析表格、修改文档”等目标。
- 不知道 Node.js、tmux、PATH、Git 仓库、worktree、CLI 或 Provider 的含义。
- 不知道一个本地服务为什么需要地址、端口和访问密码。
- 对文件是否会被覆盖、资料是否会上传、AI 是否仍在运行非常敏感。
- 遇到终端报错、空白页面或英文错误码时，通常无法自行恢复。

### 2.2 用户真正想完成的工作

用户不是来“创建 Fleet 和 session”的，而是来完成这些任务：

- 选择一批本地资料，让 AI 阅读、归纳或整理。
- 持续和同一个 AI 助手讨论一个项目。
- 把耗时任务交给 AI，并知道它现在在做什么、是否需要自己介入。
- 在电脑和手机之间继续同一项工作。
- 在应用改动文件之前看到影响范围，并能撤销。

### 2.3 两类角色必须拆开

当前流程隐含所有用户既是服务器管理员，又是最终使用者。现实中至少存在两类角色：

| 角色 | 典型场景 | 应该看到的入口 |
|---|---|---|
| 主机管理员 | 在一台 Mac/Linux 电脑上部署 MultiCC，管理 AI 账号、文件权限和服务 | “在这台电脑上安装 MultiCC” |
| 普通使用者 | 同事已经部署好，自己只需要用 Web 或 App 连接 | “扫码加入已有 MultiCC” |

如果不拆角色，普通用户会被迫理解服务器 URL、端口、Access Token 和网络策略；管理员也无法用一个安全、短期、可撤销的方式邀请使用者。

## 3. 当前新手旅程

| 阶段 | 用户预期 | 当前体验 | 主要风险 | 优先级 |
|---|---|---|---|---|
| 了解产品 | 一句话知道能帮我做什么、是否适合我 | 首页和文档先介绍多 CLI、worktree、Provider 等能力 | 无法把工程能力映射到办公任务 | P1 |
| 安装 | 下载、双击、按向导完成 | 复制 `curl` 到终端；自行处理 Node、tmux、CLI 登录、PATH 和权限 | 大量用户在看到产品 UI 前流失 | P0 |
| 首次启动 | 自动打开应用并告诉我下一步 | 终端输出多个 URL、命令、Token 和网络提醒 | 信息过载；不知道应该复制哪一项 | P0 |
| AI 就绪 | 登录一个 AI 账号即可 | 用户需要理解 CLI 自带登录、官方账号、API Provider 等多条路径 | 配置看似完成，实际不能对话 | P0 |
| 建工作区 | 点“选择文件夹” | “新建 Fleet”要求填写名称和绝对路径，并提到 Git | 用户不知道路径格式，也不理解是否会修改原文件 | P0 |
| 建对话 | 使用推荐默认值开始 | 同时出现多个 CLI × Chat/Terminal 选项 | 选择负担大，且 Terminal 对普通用户不安全 | P0 |
| 新手引导 | 带我完成一次有价值的任务 | 四步引导讲 Fleet、session、worktree、分支和多 Agent 合并 | 教的是架构，不是结果；没有完成验证 | P0 |
| 日常对话 | 像常见聊天工具一样提需求 | 顶部和底部同时暴露模型、Provider、effort、角色、记忆、commit、merge、调试等控件 | 主任务被系统控制项淹没 | P1 |
| 观察进度 | 知道 AI 正在做什么、多久、是否卡住 | 状态、后台任务、工具卡、配额、分支状态分散展示 | 用户难以形成单一判断 | P1 |
| 完成与应用 | 明确知道产出了什么，下一步是什么 | “完成”、commit、merge、主分支等概念并存 | 误以为 AI 已完成，或不敢应用结果 | P0 |
| 错误恢复 | 告诉我原因和一个下一步 | 许多路径仍暴露技术错误、原始状态或空页面 | 用户只能退出或求助 | P1 |
| 手机连接 | 安装 App，扫码连接 | Flutter 设置页要求服务器 URL 和 Access Token；仅检查地址非空 | 错误配置被带入首页，像服务故障 | P0 |
| 长期使用 | 首页只显示与我有关的待办和结果 | 管理台同时展示服务配置、网络、Provider、资源、调试与任务 | 导航按系统模块组织，不按用户工作组织 | P1 |

## 4. 关键证据

本次结论来自代码与真实界面的双重走查，主要证据如下。

### 4.1 安装与文档

- 中文 README 的稳定安装命令仍固定在 `v1.6.4`。
- `docs/installation.md` 和 `app/README.md` 仍出现 `v1.5.2`。
- 当前根包版本为 `1.6.7`，Flutter App 版本为 `2.29.12+125`。
- `install.sh` 只支持 macOS/Linux 的终端安装，并要求用户理解或处理 Node.js、tmux、至少一个已登录的 AI Coding CLI。
- 安装结束后终端一次性输出本地地址、局域网地址、聊天页、管理页、Access Token、防火墙提示和多条服务命令，没有一个明确的“下一步”主操作，也不会打开浏览器继续向导。

这不仅是文档维护问题。版本不一致会直接破坏新手对安装是否正确、安全补丁是否最新的信任。

### 4.2 Web 首次使用

- 新手引导第一步就解释“Fleet 是一个 Git 仓库”，第二步引入 session、子 Agent、worktree 和分支。
- 引导的首次成功示例是拆分前后端任务到两个 session，再 commit 和 merge；这属于进阶协作任务，不适合作为第一次体验。
- “新建 Fleet”弹层要求手工输入绝对路径，没有系统文件夹选择器、最近使用位置或创建前验证摘要。
- “新建 Session”将多个 CLI 和 Chat/Terminal 组合并列展示，没有“推荐”入口、适用场景说明或就绪状态。
- 管理首页同时存在工作区、任务中心、定时任务、记忆图谱、语音、Goal、Provider、全局设置、推送、隧道、消息桥、Agent 资源、Skills 和上传等入口。
- Chat 页同时展示连接状态、CLI、模型、Provider、effort、角色、记忆、自动提交、分享、重启、合并、调试、配额、分支和后台任务等控制项。
- 工具执行以 Bash 等底层工具卡直接进入主消息流。对办公用户而言，“Bash done”不是有意义的任务进度。

### 4.3 Flutter App 首次连接

- 首屏品牌副标题仍为 “Claude Code Chat”，与当前多 CLI 产品定位不一致。
- 用户需要填写原始服务器 URL 和 Access Token，虽然有局域网发现，但没有扫码配对主路径。
- 点击连接时只校验服务器地址不为空，随后立即保存配置并进入首页；没有验证可达性、认证、协议版本、证书或服务器身份。
- 错误地址、错误 Token 和服务未启动会在进入首页后表现为加载失败，责任边界不清楚。
- App 抽屉把工作区入口和 10 个设置入口一起呈现；对普通用户来说仍是管理控制台的信息架构。

### 4.4 手机配对

- Web 的 QR 入口使用服务器地址生成管理页二维码。
- 当前二维码不完成安全配对；手机仍可能需要额外处理访问密码。
- 文档描述与实际行为存在差异：文档暗示二维码包含可直接使用的连接信息，而实际返回的服务器 URL 不含长期访问凭证。

不建议简单地把长期 `ACCESS_TOKEN` 塞入二维码。正确方案应是短期、一次性、可撤销的配对票据。

## 5. 问题清单与改进建议

### 5.1 P0：阻断首次成功

#### P0-1 缺少消费级安装入口

**问题**

终端一键脚本对开发者很方便，但对办公用户不是“一键安装”。它要求用户跨过终端安全警告、系统依赖、权限、CLI 登录和服务管理等多个门槛。

**建议**

- macOS 提供签名、可验证来源的 `.dmg` / `.pkg` 或菜单栏 Host App。
- 安装器内完成依赖检测、后台服务安装、开机启动和浏览器打开。
- Linux 保留脚本，但包装成分步向导和明确的检查结果。
- 如果目标用户包含 Windows，必须提供正式 Windows/WSL 路径；否则在下载前明确标注当前支持平台，避免用户安装到一半才发现不支持。
- 终端脚本保留为“高级安装”，不再作为普通用户唯一入口。

**验收标准**

- 用户不打开终端即可在受支持桌面平台完成安装。
- 失败时显示“哪个检查失败、为什么、如何一键修复”，不只显示日志。
- 安装完成后自动进入 Web 设置向导，而不是停在终端说明页。

#### P0-2 首次设置没有“就绪闭环”

**问题**

当前安装完成、服务可访问、AI CLI 已安装、AI 账号已登录、Provider 可用是多个彼此独立的状态。用户可能进入首页，却无法判断为什么不能发送任务。

**建议**

首次进入时展示统一的系统就绪检查：

1. MultiCC 服务正常。
2. 存储目录可写。
3. 至少一个 AI 引擎已安装。
4. 至少一个 AI 账号/服务已验证可用。
5. 当前工作区可访问且具备所需权限。

每项只显示“已就绪 / 需要处理”，并提供一个主操作。Provider、环境变量和 CLI 登录细节放进展开项。

**验收标准**

- 未满足最低条件时不能假装设置完成。
- “AI 不可用”必须归因到安装、登录、额度、网络或配置中的一种。
- 修复后可在原地重新检测，无需重启向导。

#### P0-3 技术对象代替了用户对象

**问题**

“新建 Fleet → 选择 CLI/Terminal → 创建 session”描述的是系统内部结构，不是用户目标。

**建议**

基础模式使用以下心智模型：

| 当前术语 | 面向新手的名称 | 技术信息放在哪里 |
|---|---|---|
| Fleet | 工作区 | 详情中注明本地文件夹和版本保护方式 |
| Session | AI 助手 / 对话 | 高级详情显示 session ID |
| CLI | AI 引擎 | AI 设置的高级项 |
| Provider | AI 服务 / 账号 | AI 连接管理页 |
| worktree / branch | 安全副本 / 独立修改区 | 仅在版本详情中显示 |
| Goal mode | 带验收的任务 | 创建任务时解释“完成前会自动检查” |
| merge | 应用改动到主项目 | 确认页展示文件影响和撤销方式 |

保留原术语作为搜索关键词和高级标签，避免牺牲现有专家用户的效率。

**验收标准**

- 新用户完成首个任务不需要理解上表右侧任何技术名词。
- 所有不可逆或高风险操作均使用“用户结果 + 技术名词”的双重表达。

#### P0-4 创建工作区门槛过高

**问题**

手填绝对路径是典型的开发者输入方式。办公用户不知道文件夹地址，也不知道 MultiCC 会不会改坏原文件。

**建议**

- 主操作改为“选择文件夹”，调用系统目录选择器。
- 次操作提供“创建示例工作区”，让没有现成项目的用户先体验。
- 选择后显示确认摘要：文件夹名称、文件数量、是否已有版本记录、预计权限、是否只读开始。
- 对普通文件夹，可在明确告知后自动建立隐藏的本地版本保护；不要要求用户先学 Git。
- 首次任务默认只读，直到用户明确允许写入。

**验收标准**

- 用户不输入路径字符串即可创建工作区。
- 选错目录可返回重选，系统不会留下半成品 Fleet。
- 创建前明确展示“会读取什么、会修改什么、如何撤销”。

#### P0-5 创建对话存在选择过载

**问题**

多个 CLI 与 Chat/Terminal 的笛卡尔积被当作同级选项。新用户没有信息判断差异，选择错误也很难发现。

**建议**

- 基础模式只有一个主按钮：“开始对话”。
- 系统根据就绪状态选择推荐引擎，并显示“由 Claude/Codex 等提供支持”的弱化说明。
- 只有两个用户任务类型：普通对话、带验收的任务。
- Terminal 只在高级模式出现，并附带风险说明。
- 当只有一个 AI 引擎可用时不显示选择器；多个可用时提供“推荐 / 更快 / 更省 / 更擅长代码”等结果导向标签。

**验收标准**

- 默认路径不需要做模型或终端选择。
- 不可用选项不应在点击后才报错，应提前显示原因和修复入口。

#### P0-6 新手引导没有带来第一次价值

**问题**

当前引导讲解架构，并把多 Agent 拆分、commit、merge 作为首次练习。这既抽象又带来不必要的风险感。

**建议**

将引导改成可执行任务清单：

1. 选择或创建一个示例工作区。
2. 确认一个 AI 服务已经就绪。
3. 发送一个安全的只读任务，例如“概括这个文件夹里有哪些内容”。
4. 在统一进度卡中观察 AI 的工作。
5. 查看结果和引用来源。
6. 可选：让 AI 创建一个新文件，并演示预览、应用和撤销。

每一步都必须由系统事件自动判定完成，不靠用户手动点击“下一步”。

**验收标准**

- 引导完成条件是“收到第一份有效结果”，不是“看完四页说明”。
- 中途退出后可从上次步骤恢复。
- 空安装、已有项目和受邀手机用户分别有独立路径。

#### P0-7 App 连接流程不验证连接

**问题**

Flutter 设置页目前只判断地址非空。任何格式正确但不可达的地址都会被保存并进入首页。

**建议**

- 默认入口改为“扫描电脑上的配对二维码”。
- 手动连接放在次级入口，输入时实时验证 URL 格式。
- 点击连接后按顺序检查：网络可达、MultiCC 身份、协议版本、认证、最低兼容版本和 HTTPS 安全性。
- 成功后显示服务器名称与设备名称，让用户确认连接对象。
- 失败留在设置页，并给出唯一的下一步，例如“在电脑上打开 MultiCC”“检查是否处于同一 Wi-Fi”“重新生成配对码”。
- 历史服务器只保存已成功验证的连接。

**验收标准**

- 错误地址或错误凭证绝不进入首页。
- 每种常见失败均有用户可执行的恢复动作。
- App 与服务器版本不兼容时，在连接前明确提示升级哪一端。

#### P0-8 安装版本与说明不一致

**问题**

README、安装文档、App 文档和实际包版本不一致。新手无法判断自己是否安装了正确版本。

**建议**

- 稳定版本号只能有一个数据源，由发布脚本自动更新 README 和安装页。
- 文档中的安装命令不要手工复制版本号；使用稳定重定向地址，或在发布 CI 中生成。
- 文档测试增加“所有公开稳定版本引用必须等于当前 release manifest”的检查。
- App 下载、服务端和文档同时展示兼容范围，而不是只展示各自版本。

**验收标准**

- 发布后 README、安装页、下载页、App 更新页显示同一稳定版本。
- CI 在发现陈旧版本引用时阻止发布。

### 5.2 P1：降低日常理解与恢复成本

#### P1-1 首页按系统模块组织，而不是按用户工作组织

**建议的信息架构**

基础模式首页只保留：

- 需要我处理：等待确认、连接失效、任务失败。
- 正在进行：任务名称、当前阶段、预计等待方式、取消入口。
- 最近完成：结果摘要、变更数量、打开结果。
- 工作区：最近使用的文件夹和“新建工作区”。

Provider、隧道、消息桥、Agent 资源、Skills、上传和全局配置统一进入“设置 → 高级”。定时任务和记忆只在用户实际启用后进入一级导航。

#### P1-2 Chat 控件密度过高

**建议的基础模式 Chat**

- 顶栏：返回、对话名称、一个可理解的状态、“更多”。
- 消息区：用户消息、AI 结果、引用和必要的确认。
- 输入区：附件、输入框、发送/停止。
- 进度：合并为一张“AI 正在处理”卡，展示 3–5 个用户可理解的阶段。
- “更多”中收纳模型、角色、记忆、自动提交、分享、重启进程、调试等控制。
- 分支、配额、Provider 和工具调用默认隐藏，可按需展开“技术详情”。

#### P1-3 工具日志不是用户进度

将 `Bash done`、工具名和原始耗时转换为结果导向状态：

| 技术事件 | 基础模式文案 |
|---|---|
| 读取文件/搜索 | 正在了解工作区内容 |
| 修改文件 | 正在准备修改建议 |
| 运行测试 | 正在检查结果 |
| 等待用户输入 | 需要你确认一项选择 |
| 工具失败后重试 | 遇到问题，正在尝试其他方法 |
| 无进展 | 任务似乎卡住了 · 查看原因 / 停止 |

原始工具轨迹应保留在“技术详情”，供高级用户和排障使用。

#### P1-4 “完成”缺少统一定义

一个任务完成后应统一展示：

- AI 做了什么。
- 产生了哪些文件或内容。
- 哪些验证已通过，哪些未通过。
- 是否已经应用到主工作区。
- 用户下一步可以“查看、应用、撤销、继续修改”中的哪一项。

不要让“模型停止输出”“工具执行成功”“任务验证通过”“改动已合并”都使用近似的完成视觉。

#### P1-5 错误信息缺少恢复路径

所有错误遵循同一模板：

1. 发生了什么：普通语言的一句话。
2. 受影响的范围：本任务、AI 账号、服务器还是网络。
3. 数据是否安全：是否已经修改文件。
4. 推荐动作：只有一个主按钮。
5. 技术详情：可复制、默认折叠。

典型错误至少覆盖：服务未启动、AI 未登录、余额/配额不足、网络不可达、工作区无权限、任务卡住、App 与服务器版本不兼容。

#### P1-6 缺少安全感和可撤销预期

- 首次进入工作区时说明“默认在独立副本中操作”。
- 写入前展示权限范围；高风险动作使用二次确认。
- 应用改动时用“应用到主项目”作为主文案，`merge` 作为技术补充。
- 确认页展示变更文件数、删除项、未提交项和撤销方式。
- 重启服务、删除会话、清空上下文、删除工作区使用不同风险级别，不能都表现为普通按钮。

#### P1-7 中英文与产品称谓不一致

当前可见界面仍混用 Fleet、Provider、processed、Chat、Terminal、Save、Access Token 等词；App 仍显示 “Claude Code Chat”。

建议建立产品词汇表和 lint：

- 同一对象只有一个主名称。
- 基础模式不出现未解释的英文工程术语。
- 中文界面里的按钮、占位符、Tooltip 和错误必须完整本地化。
- 品牌副标题描述产品价值，而不是绑定单一 CLI。

#### P1-8 手机连接需要安全的配对协议

目标不是“二维码里放服务器 URL 和长期密码”，而是：

1. 电脑端生成 5 分钟有效的一次性配对票据。
2. App 扫码后与服务器交换设备凭证。
3. 电脑端显示设备名称并要求确认。
4. 每台设备可单独撤销，不影响其他设备。
5. 配对完成后不再暴露长期 Access Token。

### 5.3 P2：形成可持续的新手支持体系

- 增加全局“我该从哪里开始”入口，而不是只提供功能说明。
- 空状态给出一个推荐动作和示例，不只显示“暂无数据”。
- 给工作区、AI 服务、任务状态提供上下文帮助，避免长篇静态说明常驻页面。
- 增加命令面板/全局搜索，支持用用户语言搜索“换账号”“连接手机”“停止任务”。
- 对键盘、VoiceOver/TalkBack、动态字体、色彩对比、44pt 触控目标建立发布检查。
- 为通知说明触发条件；默认只推送“需要我处理”和“耗时任务完成”。
- 费用和额度以“本任务预计/已使用”呈现，并提供预算上限，不要求用户理解 token 细节。
- 在本地优先、用户同意的前提下记录漏斗事件，用于定位真实流失点。

## 6. 目标体验蓝图

### 6.1 路径 A：自己安装主机端

1. 用户下载并打开桌面安装器。
2. 安装器说明数据存放位置、网络访问范围和所需权限。
3. 自动检查服务与依赖；能自动修复的直接修复。
4. 浏览器自动打开 `/setup`。
5. 用户选择“登录已有 AI 账号”或“填写 API Key”；系统真实验证一次。
6. 用户通过系统选择器选择文件夹，或创建示例工作区。
7. 系统创建推荐 AI 助手。
8. 用户发送一个只读示例任务并获得结果。
9. 向导结束，进入精简首页。

### 6.2 路径 B：连接别人已经安装的 MultiCC

1. App 首屏选择“扫码连接”。
2. 管理员在电脑端点击“添加设备”，生成短期二维码。
3. App 完成服务器身份、版本和网络校验。
4. 电脑端确认设备名称与权限。
5. App 直接进入“最近工作 / 需要我处理”，不出现服务器配置页。

### 6.3 路径 C：第一次完成任务

1. 首页主按钮是“开始一项任务”。
2. 用户选择工作区并用自然语言描述结果。
3. 系统推荐“普通对话”或“带验收的任务”，高级配置默认折叠。
4. 统一进度卡显示：理解资料 → 执行 → 检查 → 等待确认/完成。
5. 写入操作前，用户确认影响范围。
6. 完成页展示摘要、产物、验证和下一步。

## 7. 基础模式与高级模式

不建议为新手另造一套功能缩水的产品。基础模式和高级模式应使用相同后端状态，只改变默认展示与操作顺序。

| 能力 | 基础模式 | 高级模式 |
|---|---|---|
| AI 选择 | 自动推荐，结果导向标签 | CLI / Provider / model / effort 完整选择 |
| 工作区 | 文件夹与安全副本 | Fleet / repo / worktree / branch 详情 |
| 对话 | 普通对话、带验收的任务 | Chat / Terminal / Goal / 全参数 |
| 进度 | 用户任务阶段 | 原始工具调用、日志和 timing |
| 应用改动 | 预览并应用到主项目 | commit / merge / 分支操作 |
| 设置 | 账号、设备、通知、外观 | 路由、隧道、桥接、资源、Skills、调试 |

高级模式应是明确的用户选择，并在开启前说明“将显示开发者控制项”；不能仅依靠屏幕宽度或设备类型判断。

## 8. 分阶段实施建议

以下周期只用于产品排序，不是排期承诺。

### Phase 0：先修漏斗和信任（约 1–2 周）

- 建立稳定版本单一数据源，修正文档版本漂移。
- 重写首次引导，以“第一份有效结果”为完成条件。
- 新建对话增加推荐默认项，基础路径隐藏 Terminal。
- Web 和 App 统一核心术语，完成中文界面清理。
- Flutter 连接前增加真实健康检查和错误分型。
- Chat 增加基础模式：收纳高级顶栏控件，折叠原始工具日志。
- 首页增加“需要我处理 / 正在进行 / 最近完成”。

### Phase 1：完成真正的新手设置（约 3–6 周）

- 新增 `/setup` 向导与 AI 就绪检查。
- 接入系统文件夹选择器和示例工作区。
- 建立一次性扫码配对协议及设备管理。
- 统一任务完成页、错误恢复卡和安全确认页。
- 将管理配置从基础导航移入高级设置。

### Phase 2：降低安装与跨设备门槛（约 6–12 周）

- 提供签名桌面安装器/Host App。
- 明确 iOS 的 TestFlight/App Store 分发路径以及 Android 正式下载路径。
- 根据目标市场决定是否提供 Windows/WSL 安装器。
- 把公网连接封装成用户可理解的“远程访问”，隐藏隧道供应商和命令细节。
- 建立隐私友好的新手漏斗分析和可用性回访。

## 9. 发布验收清单

面向新手的版本至少满足以下条件：

- [ ] 支持平台在下载前明确展示。
- [ ] 安装文档、下载页、服务端和 App 版本信息一致。
- [ ] 普通用户在支持平台无需终端即可完成安装，或明确标记为技术预览。
- [ ] 未连接可用 AI 时，首页不会显示“已经可以开始”。
- [ ] AI 连接经过真实请求验证。
- [ ] 创建工作区不要求输入绝对路径。
- [ ] 首次任务默认只读。
- [ ] 新建对话存在单一推荐入口。
- [ ] 基础模式不出现 Terminal、worktree、Provider 和 merge 作为主文案。
- [ ] 新手引导以收到有效结果自动完成。
- [ ] 任务进度能归一到一个主要状态。
- [ ] “模型停止”“验证通过”“改动已应用”有不同视觉和文案。
- [ ] 每个阻断错误都有一个主恢复动作。
- [ ] 错误页明确说明文件是否被修改。
- [ ] App 错误地址、错误凭证或版本不兼容时不会进入首页。
- [ ] 手机可通过短期二维码完成安全配对。
- [ ] 设备凭证可单独撤销。
- [ ] 所有高级功能仍可在高级模式访问。
- [ ] iOS/Android 的键盘、返回、触控目标和屏幕阅读器路径完成回归。
- [ ] 新用户可在 5 分钟内完成第一个有效任务。

## 10. 衡量指标

建议按漏斗而不是页面访问量衡量新手体验：

| 指标 | 定义 | 建议目标 |
|---|---|---|
| 安装完成率 | 开始安装后成功打开设置向导 | ≥ 85% |
| AI 就绪率 | 进入设置向导后成功验证至少一个 AI 服务 | ≥ 80% |
| 首次任务启动率 | AI 就绪后创建并发送第一个任务 | ≥ 85% |
| 首次有效结果率 | 首次任务获得非错误、可查看的结果 | ≥ 75% |
| 首次价值时间 | 从打开设置向导到第一份有效结果的中位数 | ≤ 5 分钟 |
| App 首次连接成功率 | 打开 App 后一次流程完成配对 | ≥ 90% |
| 错误自助恢复率 | 出现可恢复错误后无需外部帮助恢复 | ≥ 70% |
| D7 留存 | 7 天内再次完成至少一个任务 | 持续提升，按人群分层 |

同时记录失败原因枚举，而不是采集用户文件内容或提示词。遥测默认应透明、最小化，并允许关闭。

## 11. 建议的可用性验证

在大规模开发前，先招募 5–8 位不懂开发的真实办公用户，完成以下测试：

1. 在一台未配置开发环境的电脑上安装。
2. 连接一个可用 AI 账号。
3. 选择一个包含常见办公文件的目录。
4. 让 AI 总结目录内容。
5. 让 AI 创建一份新文档并确认应用。
6. 在手机上连接同一台 MultiCC，并找到任务结果。
7. 人为制造断网、错误账号和任务卡住，观察能否自行恢复。

观察重点不是“用户是否最终做到了”，而是：在哪一步停顿超过 10 秒、说出不确定、害怕点击、寻求解释或返回上一步。

## 12. 产品边界

- 本方案不建议删除 MultiCC 的工程能力；这些能力是产品差异化来源。
- 不应通过改名掩盖文件修改风险。基础模式仍需诚实告知影响范围和撤销方式。
- 自托管、安全隔离和本地优先应继续保留，但由产品代替用户处理实现细节。
- 如果短期内不打算服务真正的非技术用户，应反向明确定位为“面向开发者/技术团队”，避免用消费级承诺吸引无法完成安装的人。

## 13. 推荐决策

如果只能选一个季度目标，建议定为：

> 完成“首次设置 + 基础模式 + 安全配对”闭环，并用真实办公用户验证 5 分钟首次价值。

这比再增加一个 Provider、桥接渠道或高级面板更能扩大可用人群。MultiCC 已经拥有足够多的能力，下一步的产品价值来自把能力编排成一条用户无需理解底层结构也能成功的路径。

## 14. 第一版实施记录（2026-09-03）

本方案的第一版已按“先修首次使用漏斗、同时不打断老用户”的原则落地：

- Flutter App 首次连接会先验证 URL、安全传输范围、MultiCC 身份、访问密码、服务就绪状态和 App 协议版本；失败留在原页，且不会保存错误地址或密码。
- 新安装默认进入基础模式；升级前已有连接的用户继续使用开发者模式，避免熟悉的控制项突然消失。用户可在首页侧栏或设置页随时切换。
- 基础模式侧栏只展示工作入口和常用设置；创建对话只有一个推荐入口，隐藏 Terminal、CLI、Provider、model、effort 和角色配置。
- 基础模式 Chat 顶栏保留返回、名称、连接状态和更多菜单；原始工具卡、token、耗时和上下文用量默认收进“技术详情”。
- App 空状态和添加工作区流程改用“工作区 / 电脑上的文件夹 / 安全副本”等用户术语，并主动展示服务器电脑上的文件夹列表。
- Web 新手引导改为“选择工作区 → 开始对话 → 发送只读任务 → 收到第一份有效结果”，检测到真实 assistant 回复后自动完成最后一步。
- README、中文 README、安装文档和安装脚本的稳定版本统一由 `package.json` 校验；CI/测试会阻止版本引用再次漂移。

本版没有宣称完成完整 Phase 1/2。桌面图形安装器、统一 `/setup` AI 就绪向导、一次性二维码配对协议、设备撤销和 Web 全局基础模式仍按原路线图继续实施。
