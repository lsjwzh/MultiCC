# 统一通知管道与渠道插件技术方案（第二版）

版本：第二版，2026 年 10 月 28 日，取代本文件的第一版。

状态：设计稿，尚未实现。文中标“已有”的内容均已对照当前代码核实并给出位置；标“拟新增”的均为提案，当前不可用。路径相对于项目根目录。

## 一、结论

1. **只有一条通知管道。** 凡是要主动告诉用户的事（任务出错、等你回答、执行完成、业务提醒、定时任务故障），最终都进入同一个 Rust 通知引擎。引擎决定发不发、何时发、合并成什么、发给谁，并留下发送记录。现有推送（网页推送、App 推送、Bark、全局 webhook）分阶段迁入；迁完后系统里不再有第二个扇出点。
2. **渠道适配器只管发。** 适配器拿到一条已经定稿的消息和一个已经确认的目标，交给渠道，并如实回报结果等级。外部插件是适配器的一种形态，不是唯一形态。
3. **提醒意图取自“待办问题”。** 任务级的“出错 / 等待回复”，以及“这一次问题发生的时刻”，现有代码已经算好；用户的“忽略”也已有明确语义。引擎以它为主来源，用快照比对代替事件流，重启后天然可恢复。
4. **先上结果确定的渠道。** 首版主力是 webhook 模板渠道（企业微信群机器人、钉钉、飞书自定义机器人、Telegram 机器人、自定义 JSON 等），用它们把去重、合并、限频、重试、恢复做扎实。
5. **微信拆成两个适配器。**
   - iLink 私聊：唯一不经大模型、不操作桌面的个人微信官方途径，但会话窗口和条数限制各方说法不一，先实测再上线。
   - 桌面中转（发群）：沿用现有中转会话，标为实验性、默认关闭，只承诺“已交给中转”。

## 二、与第一版的主要差异

| 第一版 | 第二版 | 原因 |
| --- | --- | --- |

| “需要交互”并入“等待用户” | 默认不提醒，先用历史数据统计频率 | `src/classify/vocab.js:163` 中只要阶段不是 done 就判为需要交互，出现频率高 |

## 四、目标架构

```mermaid
flowchart LR
    subgraph 来源（Node 薄适配）
        A1[待办问题快照]
        A2[运行结果<br/>原 triggerPush]
        A3[业务通知 / 定时任务故障 / 事件规则 notify]
    end
    A1 --> E[Rust 通知引擎<br/>规则 · 意图 · 去重 · 合并 · 限频 · 重试 · 记录]
    A2 --> E
    A3 --> E
    E --> R1[Rust 内置适配器<br/>webhook 模板]
    E --> H[宿主内置适配器<br/>网页推送 · FCM · Bark · 全局 webhook · iLink · 桌面中转]
    E --> P[外部插件<br/>同步发送]
    R1 --> E
    H --> E
    P --> E
    E --> UI[设置页 · 发送记录]
```

职责边界：

- **来源**只回答“现在有哪些需要提醒的事”。它不判断发不发，也不知道渠道。
- **引擎**是规则、意图、投递状态和限频的唯一归属。
- **适配器**只回答“这条消息交出去了没有、到了哪一级”。它不保存规则，也不做合并。

## 五、提醒从哪来

### 5.1 待办问题（主来源，任务级）

- **意图键**：`任务编号 + 类别（error / waiting）+ 本次问题发生时刻`。这个时刻沿用 `todoProblemOf` 的取法，优先用会话 `taskState.endedAt`，等待类再用 `pendingUserInput.createdAt` 兜底。它只随状态变更，改名、移动、已读都不会改变它。
- **快照内容**：宿主拟新增 `listTodoProblems()`，复用 `projectRunStateOf` / `todoProblemOf` 和任务板的可见集合。每项包含任务编号、项目编号、标题、类别、发生时刻、是否已忽略、错误类别、是否用户取消。
- **何时取快照**：
  - 会话分类状态变化后，防抖约 2 秒取一次；
  - 每 60 秒兜底再取一次；
  - 服务启动后立即取一次。
- **引擎比对规则**：

  | 情况 | 处理 |
  | --- | --- |
  | 出现新的意图键 | 建立意图，交给规则匹配 |
  | 意图键消失（问题已解决） | 标记已解决，取消尚未发出的投递 |
  | 用户忽略 | 标记已忽略，同样取消 |
  | 同一任务出现新的发生时刻 | 视为新的一次问题，重新提醒 |

- **默认排除**：
  - 用户主动取消的任务；
  - `cancel_shutdown`（服务重启或关闭打断，否则每次重启都会集中报错）；
  - 已归档任务；
  - 规则里配置的排除任务；
  - 桌面中转自身所在的任务。
- **首次启用只登记不发送**：规则第一次启用时，把当前已存在的意图记为基线，只对之后新出现的意图提醒。这是 2026-09-27 那次一次投出 12 条的教训。
- **“需要交互”**：第零阶段先统计历史出现频率，再决定是否作为可选类别，默认不开。

为什么不用事件中心作主来源：事件中心只保存在内存、按会话发出、序号重启归零，作主来源需要额外一层持久化和对账。快照比对在重启后直接与库里的意图对齐。两者都无法补回“服务停机期间出现又消失”的状态，所以可靠性边界相同，而复杂度差一个量级。事件只用来触发及时取快照，降低延迟。

### 5.2 运行结果（会话级，兼容现有推送）

现有 `triggerPush` 覆盖的是会话级结果，包括执行完成，也包括不在任务板上的终端会话。第二阶段把这些调用改为向引擎提交：

- 提交内容：来源 `run_outcome`、会话编号、类型、分类字母、目标子状态、文案、发生时刻。
- 意图键：`会话编号 + 类型 + 本轮落判时刻`。取不到落判时刻时，用提交时刻，并只做短窗去重。现有的 8 秒冷却改由引擎的同会话最短间隔实现。
- 迁移后默认生成一条规则：“所有运行结果 → 本机已登记的推送设备”，保持现有行为不变。

### 5.3 其他来源（第三阶段）

| 来源 | 接入方式 |
| --- | --- |
| 业务通知 | 现有业务推送请求契约不变（去重键、409），内部改为向引擎提交 |
| 定时任务故障 | `notifyBroken` 改为提交来源 `cron_failure` |
| 事件规则的 `notify` 动作 | 事件规则仍决定“何时触发”，投递交给引擎的默认路由；事件规则不再直接调用推送 |

## 六、Rust 通知引擎

### 6.1 职责与语言边界

**Rust 负责**：规则存储与校验、意图比对、去重、合并、限频、重试与过期、投递状态机、消息模板、Rust 内置适配器的 HTTP 发送、数据库与迁移。

**Node 只负责**以下几类：
- 来源适配：快照生成、`triggerPush` 改为提交；
- 宿主内置适配器的实际发送：网页推送依赖现有 Node 库，FCM、Bark 发送与设备登记、iLink 桥接、中转会话接口都在 Node；
- HTTP 路由；
- 保险箱读取。

保留 Node 的原因是这些集成目前只有 Node 实现，立即迁移会扩大风险。保留范围是“把引擎给出的定稿消息交给现有发送函数，并回报结构化结果”。迁移条件：对应渠道有 Rust 实现，并通过同一套适配器契约测试。原生模块缺失时，通知功能整体显示“不可用”，配置保留；不提供 Node 业务回退。

### 6.2 执行模型

- 引擎在 Rust 内有一个调度线程和有界发送线程（建议 2 个），不占用 Node 的 libuv 线程池。
- 到期的投递分两路处理：
  - Rust 内置适配器：直接在发送线程执行。
  - 宿主内置适配器：通过一个回调唤醒 Node；Node 领取任务（带租约代次）并执行，然后回报结果。迟到的旧代次回报会被丢弃。
- 来源提交和快照比对都在一个短事务内完成，网络等待不占数据库事务。
- 时钟可注入，便于测试合并窗口、限频和重试。

### 6.3 数据

数据库位于 `${数据根目录}/notifications/notifications.sqlite`，路径由 `src/paths.js` 统一给出，不放进任务工作树或插件目录。采用 WAL 模式加 `synchronous=NORMAL`，开启外键和有界忙等待。

| 表 | 主要字段 | 约束 |
| --- | --- | --- |
| `destinations` | 编号、适配器类型、显示名、非敏感配置、凭据引用、版本、启用 | 只存凭据名称；修改即递增版本 |
| `rules` | 编号、名称、启用、来源与类别、范围（项目、任务、排除项）、目标列表、模板、策略、基线时刻、版本 | 通知规则的唯一归属 |
| `intents` | 编号、来源、意图键、任务/会话/项目、类别、发生时刻、标题快照、状态（活动/已解决/已忽略/基线） | `(来源, 意图键)` 唯一 |
| `deliveries` | 编号、目标及其版本、规则、正文快照与哈希、状态、结果等级、下次执行时刻、尝试次数、租约代次、过期时刻 | 每个目标一条；开始发送后正文冻结 |
| `delivery_items` | 投递编号、意图编号、目标编号 | `(意图, 目标)` 唯一，保证同一意图对同一目标只投一次 |
| `attempts` | 编号、投递编号、租约代次、起止时间、结果、回执、错误码、脱敏说明 | 只追加，不覆盖 |

已解决、已忽略、已终结的记录保留 30 天后清理；未完成的投递不清理。

### 6.4 投递状态

| 状态 | 用户看到的含义 | 后续 |
| --- | --- | --- |
| `queued` | 已排队 | 等待合并窗口、限频或渠道可用 |
| `sending` | 正在发送 | 持有租约，执行一次发送 |
| `retry_wait` | 暂时失败，稍后重试 | 到期后再次发送 |
| `sent` | 已发出，并附结果等级 | 终态；结果等级见下文 |
| `unknown` | 结果不明，可能已发出 | 不自动重发；由用户在记录页决定 |
| `failed` | 明确失败或达到重试上限 | 显示原因，可手动重试 |
| `cancelled` | 已取消 | 原因：已解决 / 已忽略 / 已过期 / 规则或目标停用 / 手动取消 |

`sent` 的结果等级由适配器如实给出，界面按等级显示，不统一写成“已送达”：

| 结果等级 | 界面文案 |
| --- | --- |
| `handed_off` | 已交给中转 |
| `accepted` | 渠道已接受 |
| `delivered` | 渠道给出了送达证据（本方案首批渠道都达不到这一级） |

### 6.5 合并、限频、重试

- **合并**：同一目标、同一规则的意图在合并窗口内合并成一条消息。开始发送后不再追加。发送前复核每个意图：已解决或已忽略的剔除；全部被剔除时取消这条投递。
- **限频**：以目标为维度，合并后的一条消息计一次。额度不足时只推迟“下次执行时刻”，内容留在库里，不丢弃。
- **默认值**：

  | 规则类型 | 合并窗口 | 同目标最短间隔 | 每小时上限 | 重复催办 |
  | --- | --- | --- | --- | --- |
  | 待办类（微信、群机器人） | 30 秒 | 120 秒 | 12 条 | 关 |
  | 迁移来的设备推送 | 0 | 同会话 8 秒（与现状一致） | 不限 | — |

- **重试**：
  - 网络未连通、429、5xx 可重试，按 5 秒、30 秒、2 分钟、10 分钟退避并加抖动，最多 5 次；渠道给出等待时间时以渠道为准。
  - 4xx（429 除外）判为明确失败。
  - 请求已经发出但没拿到响应，判为 `unknown`，不自动重发。只有声明支持幂等的适配器才自动重试。
- **过期**：投递创建 6 小时后仍未发出，取消并标记过期。
- **总开关**：全局一键暂停所有发送，排队内容保留。

### 6.6 启动恢复

1. 处于 `sending` 且没有结果的投递记为 `unknown`。
2. `queued` 和 `retry_wait` 按原计划继续。
3. 立即取一次待办快照，与库中意图对齐：消失的标记已解决；新出现的按 5.1 处理。

服务重启只能由用户手动触发。本方案不改变这一点。

## 七、渠道适配器

### 7.1 统一契约

所有形态的适配器都实现同一组语义，外部插件用 JSON 输入输出表达：

| 操作 | 输入 | 输出 |
| --- | --- | --- |
| `describe` | 无 | 支持的目标类型、最大长度、是否支持 Markdown、结果等级上限、是否幂等、是否需要桌面、建议频率 |
| `validate` | 目标配置 | 配置是否完整、目标摘要；不发送消息 |
| `send` | 投递编号、尝试编号、幂等键、目标（含版本）、定稿正文、过期时刻 | 结果、结果等级、回执、建议等待秒数、错误码、脱敏说明 |

`send` 的结果只能是以下之一：

| 结果 | 含义 |
| --- | --- |
| `sent` | 已发出（附结果等级） |
| `retryable` | 暂时失败，可重试 |
| `permanent` | 明确失败，不再重试 |
| `blocked` | 需要用户处理，例如登录失效、窗口过期 |
| `unknown` | 结果不明 |

正文和目标在发送前已经冻结。目标改动后，正在重试的旧消息暂停并提示重新确认，不会悄悄改发到新目标。

### 7.2 首批适配器

| 适配器 | 形态 | 结果等级上限 | 阶段 |
| --- | --- | --- | --- |
| webhook 模板 | Rust 内置 | 渠道已接受 | 第一阶段 |
| 微信桌面中转（发群） | 宿主内置，实验性，默认关闭 | 已交给中转 | 第一阶段（替换现有脚本） |
| 微信 iLink 私聊 | 宿主内置，依附现有 iLink 桥接 | 渠道已接受 | 第零阶段实测通过后 |
| 网页推送 / FCM / Bark / 全局 webhook | 宿主内置，复用 `src/push/` | 渠道已接受 | 第二阶段 |
| 外部插件 | command 型 Rust 二进制 | 由插件声明 | 第三阶段 |

### 7.3 webhook 模板（Rust 内置）

- **预设模板**：企业微信群机器人、钉钉群机器人、飞书自定义机器人、Telegram 机器人、Bark（自建服务器）、ntfy、自定义 JSON。每个预设规定 URL 格式、请求体格式、签名方式和成功判据。
- **凭据**：URL 里的令牌和签名密钥通过保险箱输入，配置里只存名称。
- **出网**：沿用宿主的出网代理设置。Telegram 等境外服务在国内网络下需要代理，测试发送时提示具体原因。
- **界面如实说明消息到哪里**：
  - 企业微信群机器人的消息在企业微信群里，需要用企业微信 App 接收，不会进个人微信；
  - Server 酱一类第三方转发服务会经过第三方服务器，由用户自行决定是否使用；
  - 选择任一外发渠道时都提示“任务标题会离开本机”。

### 7.4 微信 iLink 私聊

已知约束（来自代码和外部资料，后者需实测）：

- 发送必须带 `to_user_id` 和 `context_token`（代码已核实）。
- 外部资料称：令牌在用户给机器人发消息后约 24 小时内有效，窗口内可能有约 10 条上限，只能发私聊、不能发群；缺少某些隐藏字段时消息会被静默丢弃。

设计要点：

- **一个机器人令牌只能有一个轮询者。** 通知适配器不自己调用 `getupdates`，而是复用 iLink 桥接的轮询；否则两边会互相抢走消息。
- **桥接增加“仅通知”模式**：只轮询、刷新令牌、处理绑定码，不把收到的消息转进聊天会话。
- **令牌按用户持久化**：桥接把每个用户最近一次的 `context_token` 和收到时间加密保存，不再只放在内存里、只记当前用户。
- **绑定流程**：设置页显示绑定码，用户用自己的微信给机器人发这个码，即完成目标绑定。
- **窗口过期**：投递状态为 `blocked`，界面提示“请给微信机器人发任意一条消息以恢复提醒”。不靠别的渠道去催这一步，避免循环依赖。
- **结果等级最多到“渠道已接受”**。

第零阶段实测清单：

- 窗口时长；
- 条数上限；
- 服务重启后保存的令牌是否仍可用；
- 超出窗口时接口如何报错；
- 静默丢弃能否被检测到；
- 仅通知模式是否影响聊天桥接。

任一项不满足“每天至少能稳定收到提醒”，就不作为默认微信渠道上线。

### 7.5 微信桌面中转（实验性）

- **交接方式**：引擎把定稿正文通过 `POST /api/sessions/<中转会话>/scheduled-messages` 交给中转会话，以尝试编号作为 `Idempotency-Key`。重复交接只会得到同一条定时消息。
- **结果等级**：只到“已交给中转”。代理回复“已发送”不能升级为更高等级。以后若要更高等级，需要单独设计中转的结构化回报接口。
- **串行**：中转会话一次只处理一条消息，天然串行，不再另建桌面租约。
- **固定成本与限制**（启用时必须在界面写明）：
  - 每次发送都消耗一次模型调用；
  - 需要 MultiCC Agent 的电脑操作权限、微信桌面已登录、屏幕已解锁；
  - 坐标随屏幕和搜索词变化，需要按本机实测维护；
  - 个人微信被自动化操作存在账号风控风险；
  - 与其他会话的电脑操作可能互相干扰，仓库没有全局仲裁。
- **锁屏**：默认不自动解锁，中转判断无法发送时投递记为 `unknown`。“借用自动解锁发送”是有安全代价的选项，首版不提供。
- **迁移**：中转会话、群名、排除规则、限频参数从现有配置导入，见第十一节。

### 7.6 外部插件（第三阶段）

- 沿用现有 `plugin.json` 的 `schema: 1` 和 command 型引擎，增加 `notification` 能力声明；`commands` 至少包含 `describe`、`validate`、`send`。
- 只支持 20 秒内完成的同步发送。需要长时间操作或桌面操作的渠道，不能做成外部插件。
- 宿主调用前收紧环境：子进程只拿到系统必需变量和该目标授权的凭据，不再继承宿主全部环境变量。这项改动也会影响现有插件 `chrome-proxy-launcher`，需要单独回归。
- 页面不能通过 `/api/plugins/:id/run` 直接调用通知插件的 `send` 而绕过队列；宿主强制只开放 `describe` 和 `validate`。
- 插件是本机可信代码；限制环境变量只能降低误用，不构成沙箱。

## 八、用户怎么用（完成后的目标流程）

入口：设置 →“通知”。页面分四块：

| 区块 | 内容 |
| --- | --- |
| 目标 | 已登记的推送设备（迁移后自动出现）、webhook 模板目标、微信 iLink、微信桌面中转（实验性） |
| 规则 | 预置两条：“任务出错或等我回答 → 选定目标”，以及迁移来的“运行结果 → 推送设备” |
| 发送记录 | 每条投递的状态、结果等级、尝试记录、关联的任务 |
| 总开关与健康状态 | 引擎是否可用、各目标最近一次结果 |

操作步骤：

1. **添加目标**：选择渠道类型，按提示填写。密钥通过保险箱对话框输入；iLink 用绑定码绑定。
2. **测试发送**：点击后真实发出一条标有“测试”的消息，并显示结果等级。
3. **配置规则**：选择项目范围、类别、目标，可调合并与限频参数，保存时说明单位。新规则默认先预览，启用时只登记当前状态。
4. **查看记录与处理异常**：在记录页处理 `blocked` 和 `unknown` 的投递。对 `unknown` 重试时，界面明确提示“可能重复”。

普通用户不需要知道中转会话编号、命令参数或队列字段。

## 九、拟新增接口

所有接口复用现有鉴权与请求校验。

| 方法与路径 | 行为 |
| --- | --- |
| `GET /api/notifications/status` | 引擎是否可用、总开关、各适配器能力与健康 |
| `PATCH /api/notifications/status` | 总开关暂停或恢复 |
| `GET` / `POST /api/notifications/destinations` | 列出或创建目标（不返回凭据） |
| `PATCH /api/notifications/destinations/:id` | 修改或停用目标，递增版本 |
| `POST /api/notifications/destinations/:id/test` | 真实发送测试消息，返回投递编号 |
| `GET` / `POST /api/notifications/rules` | 列出或创建规则（新建默认停用） |
| `PATCH /api/notifications/rules/:id` | 修改、启用或暂停 |
| `POST /api/notifications/rules/:id/preview` | 用当前快照预览会命中哪些意图、文案是什么；不写投递 |
| `GET /api/notifications/deliveries`、`/:id` | 按状态、时间、规则、目标查询，查看单次详情 |
| `POST /api/notifications/deliveries/:id/retry` | 手动重试；`unknown` 需要显式确认可能重复 |
| `POST /api/notifications/deliveries/:id/cancel` | 取消尚未发出的投递 |
| `POST /api/notifications/submit` | 业务方提交通知 |

`submit` 的返回约定：

| 情况 | 返回 |
| --- | --- |
| 已写入数据库 | 202 |
| 同一幂等键、相同内容 | 返回同一投递 |
| 同一幂等键、不同内容 | 409 |
| 无权使用目标 | 403 |
| 引擎不可用 | 503 |

过渡期内，现有 `/api/push/*` 接口保持可用：第二阶段起它们内部转给引擎，第三阶段后再评估是否收敛。

## 十、安全与内容

- **消息内容**：默认只包含状态、任务标题、项目名和链接。对话内容、错误堆栈、文件路径不外发；以后若要外发，需要单独的内容开关。
- **链接地址**：优先使用用户在通知设置里确认过的访问地址，其次是隧道的公网地址 `publicUrl`。都没有时省略链接，并提示去设置。禁止写死任何个人域名，禁止给手机发送回环地址。
- **凭据**：凭据只进保险箱。不进数据库正文、命令参数、日志和发送记录。
- **防误发**：首次启用只登记不发送；每小时有上限；有全局总开关；目标修改后，旧消息暂停待确认。

## 十一、实施阶段

| 阶段 | 内容 | 完成判据 |
| --- | --- | --- |
| 第零阶段：验证（约 1 天） | iLink 实测清单（7.4）；统计近 30 天“需要交互”“出错”“等待”的出现频率，以及 `cancel_shutdown` 的占比 | 实测结论写入本文；据此确定 iLink 是否上线、默认类别与限频参数 |
| 第一阶段：引擎与待办提醒 | Rust 引擎、6 张表、状态机；待办问题来源；webhook 模板适配器；桌面中转适配器；设置页最小版；发送记录 | 第十二节第一阶段用例全部通过；现有微信提醒脚本完成切换 |
| 第一阶段补充：iLink | iLink 桥接的仅通知模式、按用户持久化令牌、绑定码、适配器 | 用真实微信连续 3 天每天都能收到提醒；窗口过期时正确提示 |
| 第二阶段：现有推送迁入 | `triggerPush` 改为提交；网页推送、FCM、Bark、全局 webhook 包装成适配器；迁移默认规则 | App、网页、Bark 收到的推送内容和时机与迁移前一致；终端会话推送不丢；`src/push/runtime.js` 不再自行扇出 |
| 第三阶段：其余来源与外部插件 | 业务通知、定时任务故障、事件规则 `notify` 接入；外部插件协议与环境收紧；邮件等新渠道 | 系统中只剩引擎一个扇出点；新渠道无需改规则即可接入 |

现有微信提醒脚本的切换（第一阶段内）：

1. 只读盘点现有定时规则、配置文件、状态文件和中转会话，确认实际在运行的发送源。
2. 导入配置：中转会话、群名、排除规则、限频参数，建立桌面中转目标和规则，并保持停用。
3. 影子运行：新规则只计算不发送，与脚本同时运行几天，对比两边认定的提醒并解释差异。
4. 切换：停用脚本的定时规则，再启用新规则。启用时以当前状态为基线，任何时刻只有一个发送源。
5. 回退：暂停新规则，恢复脚本规则。脚本有自己的状态文件，切换期间可能重复提醒一次，这是可接受代价，需事先告知。

## 十二、验收

自动化测试使用模拟适配器和隔离数据库；真实渠道使用用户指定的测试目标。

| 阶段 | 场景 | 必须观察到 |
| --- | --- | --- |
| 一 | 首次启用时已存在多个出错任务 | 只登记基线，不发送 |
| 一 | 服务重启导致多个回合被打断（`cancel_shutdown`） | 不产生提醒 |
| 一 | 30 秒内 5 个任务出错 | 每个目标只收到 1 条合并消息，包含 5 项 |
| 一 | 限频期间又出现新问题 | 内容留在库里，到期发出；不丢失 |
| 一 | 问题在发送前已解决或被忽略 | 从待发消息中剔除；全部剔除则取消 |
| 一 | 同一任务恢复后再次出错 | 作为新的一次问题再次提醒 |
| 一 | 两个目标中一个失败 | 成功的目标不重发，失败的目标独立重试 |
| 一 | 发送中途强制退出再启动 | 该投递记为 `unknown`，不自动重发；排队中的照常继续 |
| 一 | 请求已发出但超时 | 记为 `unknown`，不自动重发 |
| 一 | 目标修改后重试旧消息 | 暂停并要求确认，不改发到新目标 |
| 一 | 桌面中转重复交接同一次尝试 | 中转会话只收到一条消息 |
| 一 | 中转代理回复“已发送” | 结果等级仍为“已交给中转” |
| 一 | 原生模块缺失 | 显示“通知不可用”，配置保留，没有任何 Node 回退发送 |
| 一 | 消息链接 | 使用用户确认的地址或隧道地址；都没有时不带链接 |
| 补充 | iLink 窗口过期 | 投递为 `blocked`，并提示用户给机器人发消息 |
| 二 | App、网页、Bark 推送 | 标题、正文、跳转与迁移前一致；终端会话推送照常 |
| 三 | 业务通知同一幂等键、不同内容 | 返回 409 |
| 三 | 页面直接调用插件的 `send` | 被拒绝，投递记录不变 |
| 三 | 插件子进程环境 | 只有白名单变量和本目标授权的凭据 |

## 十三、风险与未决问题

| 风险 | 应对 |
| --- | --- |
| iLink 属于未正式公开的接口，策略可能调整 | 不作为唯一渠道；失败时显示 `blocked`，用户可另配其他目标 |
| 桌面中转有模型成本、账号风控和桌面冲突 | 标为实验性、默认关闭，界面写明限制；不承诺送达 |
| 第二阶段可能改变用户感知的推送行为 | 设备推送规则默认不合并、保持 8 秒同会话间隔，并做迁移前后对比测试 |
| 境外 webhook 需要代理 | 沿用宿主代理设置，测试发送时给出具体原因 |
| “需要交互”是否提醒 | 等第零阶段数据决定 |
| 停机期间出现又消失的状态无法补回 | 产品说明中写明这一可靠性边界 |
