# 会话消息与显示状态

会话历史文件是完整原文，不再是可以随界面清理而删除的缓存。原生 CLI 的
上下文、会话显示状态、任务消息证据有各自独立的生命周期。

## 存储与读取

- `chat_history/<session>.json`：原有 JSONL 原文，包含消息 ID、任务归属和投递凭据。
- `chat_history/.views/<session>.json`：仅保存版本号和隐藏消息 ID，原子写入。
  旧文件缺少 ID 时，先将生成的 ID 落盘，再写隐藏状态。
- 普通会话的 HTTP/WS 分页先计算 usage 投影，再过滤隐藏状态，最后应用显示上限。
  `load`/`viewHistory`、任务引用读取和投递确认继续读取完整原文。
- 任务入口使用 `historyScope=archive` 读取完整记录；会话内的隐藏广播不改变任务视图。
  该参数改变显示范围，不改变身份认证或会话访问权限。

## 操作契约

| 操作 | 效果 |
| --- | --- |
| `clear_history`，可带 `keep` | 隐藏早期已完成消息，收到持久化确认后更新所有普通会话视图 |
| `DELETE /api/sessions/:id/messages/:msgId` | 兼容旧客户端的隐藏操作，保留原文 |
| `clear_history` + `preserveHistory:true` | 原有独立上下文轮换操作 |
| 标记任务完成或归档 | 保留任务、消息引用和绑定会话 |
| 删除整个会话／目录级联删除 | 删除前检查任务引用；包括已归档任务、合并来源和共享消息 |

清理显示不停止正在运行的回复、后台任务或队列，不重置原生上下文。进行中的
助手快照仍可继续显示。清理请求失败时，不发送成功重置广播。

条数上限只限制显示，不淘汰原文；任务消息引用也不再按 500 条截断。
旧的执行槽位是例外：其原文已由 TaskRun 生命周期在清理前持久化到 SQLite 台账。

任务档案仍存在时，不能永久删除它引用的原文；`archived` 状态不表示档案已删除。
只有明确清理相关任务档案与消息，且所有其他引用均已解除，才具备物理删除条件。
当前没有新增“联合永久删除”按钮或自动回收任务档案的流程。

## 上下文追踪字段的存量

`contextTrace` 是「引用来源」面板的派生诊断数据，不是对话原文。运行时现在写入的
已经是摘要：`contextTraceFor`（src/chat/turn-engine.js）请求 `{ summary: true }`，
src/task-shell/runtime.js 的 summary 分支只返回 traceId、当前任务、来源条数与预算，
实测约 304 字节；明细由面板按需走 `GET /api/sessions/:id/context` 拉取。

2026-09 前后写入的消息内嵌的是完整对象，实测均值 113KB 一条。2026-11-14 实测主仓
775 个会话文件共 1.36GB，其中 `contextTrace` 占 53.3%，最大的几个文件里占 89–96%。
这是冷读整份历史时内存放大的主因，与条数上限无关：条数不变而字节可以差三个数量级。

`scripts/history-trace-compact.js` 把这些遗留对象降级成同形状的摘要。它只替换该字段
所在的那一段字节，并要求 `role`/`content`/`ts`/`id`/`tools`/`usage`/`taskId`/`turnId`
逐字节不变才落盘，因此不构成对原文的淘汰。定位该字段按顶层成员遍历而不是搜索字节：
讨论这个字段的会话，正文里本身就含 `"contextTrace":` 字面量。默认只做 dry-run；
`--apply` 需要 `--backup-dir`，并用 lsof 探测数据根是否被服务占用，占用时拒绝执行——
Rust 侧持有历史缓存与追加字节账本，绕过它改盘会让账本与磁盘失配。

代价是 receipt 已被回收的那部分消息，面板展开会落到既有的 `detailExpired` 态。
2026-11-14 实测 6,846 条待降级消息里，6,805 条（99.4%）的 receipt 仍在
task-shells.sqlite 中可按需取回，41 条（0.6%）已消失。

## 兼容与验证

现有文件继续直接读取，首次清理才创建展示状态文件；旧客户端的请求类型不变。
被旧版本实际删除的原文不能由这次改动恢复。

回归覆盖原文逐字节保留、重启/改名后的隐藏状态、共享和归档任务引用、旧 ID
迁移、写入失败、流式回复、独立上下文轮换，以及 Web/App 的确认后显示更新。
