# Node CPR 与 Rust CPR 对照实测

日期：2026-10-23。结论针对当前实现：建议继续默认使用 Node，Rust 保持实验选项。Rust 在部分并发场景能提高吞吐，也能正确处理跨块 UTF-8，但当前长上下文路径明显更慢，且 Codex 错误响应格式尚未与 Node 一致。

> 2026-11-06 注：Node 后端已删除，Rust 是唯一实现；本文的对照数据仅作历史记录。
> `scripts/benchmark-cpr-backends.js` 已随双后端退场一起删除。

## 测试条件

- Apple M4、macOS ARM64（Darwin 24.3.0），Node v26.8.1，安装的 `cli-provider-router` 为 0.5.2。
- 代理内核基线是已合入 MultiCC 的 `7469bb0a`；未修改生产代理逻辑进行优化。设置按钮改动不参与代理请求处理。
- 使用真实 `createProviderRouterRuntime`、`mode=cpr`、协议代理及宿主用量／增量回调，只替换供应商记录和上游为本地固定夹具。
- 客户端、模拟上游、Node 代理、Rust 代理各占独立进程；同一时刻只向一个待测后端施压。本地 HTTP/1.1、连接复用，无 TLS、外部供应商推理或真实账号。
- 六种负载、每种两档并发，共 12 个场景。每场景交错运行 Node／Rust 五轮；小请求每后端先预热 200 次，每轮 2,000 请求；大请求／大输出预热 12 次，每轮 128 请求；持续流预热 12 次，每轮 16 请求。
- 正式计时共 88,000 请求，不含预热、正确性和取消检查。正式轮次为北京时间 09:30:12–09:31:45；之前的短预跑仅用于校验夹具，不混入正式统计。
- 每个成功响应均计算 SHA-256 核对原始字节，且逐轮核对用量／结束事件数量。保留各轮原始样本；表中 P50、P95 和吞吐都是相应指标的五轮中位数。

原生模块 SHA-256：`9162f659478cecd6655a0f394f80f0ef251a33abca47e4acb9d510f45b90df57`。

## 行为差异

| 场景 | Node CPR | Rust CPR |
| --- | --- | --- |
| Claude／Codex 正常 SSE、非流式 JSON | 固定样本原始响应正确 | 与 Node 原始字节一致 |
| Claude 上游 401／429 | 保留 HTTP 状态和 JSON 正文 | 同样保留 |
| Codex 上游 401／429 | HTTP 200，生成 `response.failed` SSE，把原错误嵌入事件消息 | 保留上游 401／429 和原 JSON 正文 |
| UTF-8 中文被拆在两个上游数据块中 | Claude 与 Codex 增量回调出现替换字符 | 两种协议增量回调均保持正确中文 |
| 客户端取消 | 连接等待期、流期间均关闭上游，每次仅结束一次 | 同样成立 |

错误格式差异是实测结果，不是夹具把其中一方判为成功。两者都产生错误用量事件，但 HTTP 客户端的重试与错误解析行为可能不同，不能视作完全可互换。

UTF-8 额外检查对两协议、两后端各重复三次，共 12 次。刻意在「中」的三个 UTF-8 字节之间切块，间隔 5ms；每次输出四段 `中文🌏` 加 ASCII。Node 的六次回调文本均出现 12 个 `�`，累计 320 字节；Rust 六次均无替换字符，为正确的 296 字节。**原始 HTTP 响应两者均正确**，差异发生在旁听解析后交给宿主的增量回调，不能据此认定 CLI 收到的原始文本也乱码。

代码对应 Node CPR 的 Claude `_feedChunk` 逐块执行 `chunk.toString('utf8')`；Rust `Observer` 保留字节，在完整事件边界解析。大输出性能场景也观察到 Node 的增量文本字节数偏大，已通过上述受控切块实验确认相关解码问题。因此大输出计时是现状对照，不能当作完全等价语义的语言性能基准。

其余基本检查共 16 个 HTTP 样本：用量、成功／错误状态计数、结束次数、增量事件数及文本字节数一致。另行执行现有 CPR 集成套件，22/22 通过、无跳过；这些结果不抵消本轮新发现的差异。

## 延迟与吞吐

延迟单位为毫秒，表示客户端发出请求到完整响应结束；不是模型推理延迟。小请求正文约 2 KiB、响应约 3 KiB；长上下文内容为 1 MiB ASCII；大输出为约 1 MiB、4,096 个文本增量事件。持续流每约 2ms 发送一个事件，实际周期受系统调度影响。

| 场景 | 并发 | Node P50 | Rust P50 | Node P95 | Rust P95 | Node 请求/秒 | Rust 请求/秒 | Rust/Node 吞吐 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Claude 小请求 | 1 | 0.160 | 0.344 | 0.260 | 0.611 | 5442 | 2517 | 0.463× |
| Claude 小请求 | 16 | 1.345 | 1.535 | 2.451 | 2.371 | 10508 | 9715 | 0.925× |
| Codex 小请求 | 1 | 0.182 | 0.330 | 0.256 | 0.405 | 4776 | 2867 | 0.600× |
| Codex 小请求 | 16 | 1.826 | 1.576 | 3.496 | 2.447 | 7428 | 9308 | 1.253× |
| Claude 1 MiB 上下文 | 1 | 2.811 | 7.661 | 5.110 | 10.605 | 330 | 124 | 0.375× |
| Claude 1 MiB 上下文 | 8 | 18.895 | 35.530 | 32.324 | 49.024 | 378 | 223 | 0.588× |
| Codex 1 MiB 上下文 | 1 | 2.556 | 11.277 | 4.622 | 14.567 | 345 | 85 | 0.247× |
| Codex 1 MiB 上下文 | 8 | 16.027 | 49.200 | 26.202 | 64.766 | 462 | 156 | 0.337× |
| Claude 约 1 MiB 输出 | 1 | 4.056 | 9.163 | 5.153 | 10.659 | 235 | 107 | 0.456× |
| Claude 约 1 MiB 输出 | 8 | 27.328 | 21.283 | 30.395 | 24.455 | 287 | 374 | 1.302× |
| Claude 持续流 | 1 | 170.921 | 171.485 | 174.756 | 175.635 | 5.847 | 5.849 | 1.000× |

当前 Rust 桥接多次在 JavaScript 与 Rust 之间序列化请求、传递 JSON 字符串，且发送前再次执行准备步骤。长请求会反复承担这些成本；这是代码中可以确认的路径，但本轮未做 CPU 剖析，不能把全部差值归于某一个函数。后续优先减少重复准备与跨边界拷贝，再以同等功能的 Node 路径比较。

## CPU、主线程和取消

以下 CPU 是代理进程完成一轮的累计 CPU 时间，包含 Rust 原生线程；多核并行可能使 CPU 时间超过墙钟时间。事件循环指标为 Node 宿主的延迟直方图 P99，不代表整次请求延迟。

| 场景 | 每轮请求数 | Node CPU ms | Rust CPU ms | Node 事件循环 P99 ms | Rust 事件循环 P99 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Claude 小请求，16 并发 | 2000 | 243.134 | 735.710 | 2.191 | 1.508 |
| Codex 小请求，16 并发 | 2000 | 359.730 | 783.435 | 2.822 | 1.581 |
| Claude 长上下文，8 并发 | 128 | 430.857 | 1119.170 | 24.117 | 10.887 |
| Codex 长上下文，8 并发 | 128 | 347.598 | 1341.973 | 14.606 | 15.172 |
| Claude 大输出，8 并发 | 128 | 508.014 | 1545.850 | 21.512 | 5.923 |

Rust 在部分压力下让宿主事件循环更顺畅，但本轮各场景的累计 CPU 均更高，也没有普遍消除长请求时的主线程延迟。不能据此宣称更省 CPU。

每后端分别测试等待响应头、流期间取消各 12 次，共 48 次。由客户端销毁连接到模拟上游关闭通知被收到，Node 中位数为 0.194／0.156ms，Rust 为 0.186／0.155ms；两者均完成上游释放，每后端恰好 24 次逻辑结束事件。这包含本机 IPC 延迟，样本很小，应视为取消正确性和毫秒内量级的检查，不据此排名。

原始结果保留了进程 RSS 采样，但同一代理进程跨场景复用，受 GC、缓存和此前负载影响，未采用每场景冷进程，不能据此作严谨的内存优劣结论。

## 复现与证据

基准脚本：`scripts/benchmark-cpr-backends.js`。该 JavaScript 文件仅为测试驱动和固定上游夹具，不承载后端产品逻辑。

```sh
MULTICC_RUST_ADDON=/absolute/path/darwin-arm64/multicc_core.node \
CPR_BENCH_OUTPUT=/tmp/cpr-comparison.json \
node scripts/benchmark-cpr-backends.js
```

只执行行为检查（含 UTF-8 和取消），可再设置 `CPR_BENCH_VERIFY_ONLY=1`。默认五轮；`CPR_BENCH_ROUNDS` 可指定不少于三轮。测试会自行启动并停止隔离进程，不需要运行 MultiCC 服务。

本机原始证据存放在主仓库共享数据目录 `data/rust-cpr/2026-10-23/comparison/`：

- `performance.json`：正式 12 场景、五轮原始数据，88,000 个计时请求。
- `behavior.json`：独立补充的 UTF-8、错误格式与取消检查。
- `performance.log`、`behavior.log`：执行日志。
- `contracts.log`：22 项现有集成测试结果。

这些是本机测试产物，不加入 Git。性能计时完成后只给测试驱动补充了受控 UTF-8 检查和仅验证模式；代理产品代码和原生模块保持同一份。

## 验收边界与后续

本次比较完成，不等于真实账号／外部网络验收。未测 Node 22 安装包、TLS／HTTP/2、远程供应商延迟、真实长历史及其他 CPU／操作系统，未据此修改默认值、生产配置或重启服务。执行对比测试期间没有提交、合并或推送代码。

小请求单并发下，两者本机完整响应延迟均不足 1ms；真实聊天往往还包含网络和模型生成等待，不能把本表倍数直接换算成聊天速度倍数。Rust 的并发收益也伴随更高 CPU 开销。

若继续推进，应先统一 Codex 错误输出契约、修复 Node 增量 UTF-8 解码，并减少 Rust 桥接的重复 JSON 处理，再做等价对照和真实客户端验收。本批提交包含已验证的设置按钮、原生接口、对比脚本和报告；提交前已 rebase 到主线 `ce0df002` 并复验，尚未合入 main 或部署。本次提交不包含上述兼容性或性能问题的修复。
